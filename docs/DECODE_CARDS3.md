# Research: skills dialog, golfer card Customize / View Story, Load Game side panel

Source: `spec/golf_decomp.c` (Ghidra text only, no data bytes), plus pixel inspection of `Interface/TransPopups*.pcx`, `courseinfo.pcx`. Read first: docs/DECODE_GOLFERCARD.md, DECODE_CARDS2.md, DECODE_TITLE2.md (not repeated here unless corrected).
Tags: EXACT = read directly in the decompile. DERIVED = code plus art or arithmetic. WEAK = a plausible reading. NOT IN DUMP = the decompile does not contain it.

Housekeeping: the line numbers in DECODE_GOLFERCARD.md are about 425 too high. Actual lines: FUN_0045c560 starts at 60032, FUN_0045f0f0 at 62483, FUN_0043b610 at 34868, FUN_00466370 at 69285. Addresses and logic in those docs are fine.

## 1. Golfer stats card / skills dialog

### 1.1 Which function, who opens it (EXACT)
- Drawing function: `FUN_0045f0f0(title, learntMask, points, slot, xoff)` at line 62483. Signature and layout are already in DECODE_CARDS2 section 1; I re-read the whole body and found nothing contradicting it.
- Callers in the dump (this is the new part):
  1. `FUN_0045c560` (golfer info card), line 60064: `if (type_byte(slot) != 0) { name -> 0x51a068; FUN_0045f0f0(&0x51a068, short@0x5794ce[slot*0x100], -1, slot, -0x32) }`. So the skills panel is NOT opened by a button. It is drawn automatically every frame, behind/next to the info card, whenever the golfer's type byte `0x5794d0[slot*0x100]` is nonzero. Ordinary members and visitors have type 0, so they get NO skills panel at all.
  2. line 21344 and 21347: two calls, `(slot A, xoff 0)` then `(slot B, xoff 0x15e)` with points -1 (view only), followed by `FUN_00480c80(0)` and `FUN_0045c0c0(0)`. This is a side by side "versus" intro for a pro challenge (preceded by the string " vs " at 0x4c7474 and sound 0x2a). Two wide cards, x offsets 0 and 350.
  3. line 3907: `FUN_0045f0f0("Gary Golf" (0x4d6098, player name), 0, pointsFromTable, -1, 200)`: the player's own editable skill spend (already known).
  4. line 82420: same editable form with slot 0x9c, xoff 200, points = 13 first time or (DAT_004c2c9c != 0 ? 3 : 13) as `(-(mask!=0) & 0xfffffff6) + 0xd` i.e. 13, or 3 when a mask already exists.
- Type byte `0x5794d0` meaning (EXACT, from the setters): 0 ordinary golfer; 0x20 pro/celebrity challenger (line 13461, skills copied from pro table 0x58dd75, 12 bytes, mask bits built from nonzero skills, base mask 0xe0); 0x24 the player's own golfer in that match (line 13607; profile index 0 so skills read from the player's working copy at 0x5a59fa+10); 0x40+n "County commissioner" VIP (62243); 0x60+n "Corporate CEO" VIP (62137/62192); 0x80 "Wealthy Heiress" (62311). The VIPs get randomly chosen skill bits (3 or 4 random picks of 9 or 12) written to the mask at 0x5794ce. So the card with skills is the card of a pro, a VIP or the player in an exhibition, not of every golfer.
  Confidence: EXACT for the code path; the in-game wording of "who gets it" is DERIVED.

### 1.2 Geometry in read-only mode (points = -1, xoff = -0x32) (EXACT)
Read-only means `param_3 == -1`: no hover test, no plus/minus pad, no points line, no OK button, and the routine returns -1 right after one draw (it does NOT loop; the info card redraws it each frame).
- Frame: `FUN_0040cef0(0x1c, 0x32, 0xd0, 0x13c, 1)` = 208 x 316 at (28, 50). Right edge x=236 touches the info card header at 0xec (236).
- Title: font object 0x519928, centred (`FUN_00404bc0`) at (160, 0x3a=58), colour 0x80007fff white. Text = output of name builder `FUN_004676e0(slot, 0)` in 0x51a068 (the golfer name, built from prefix table 0x4c4974 + name + suffix 0x4c59e0).
- No portrait ring, no face, no OK sprite in the narrow variant (those are `xoff >= 0` only).
- Rows r = 0..9: y_r = 0x5a + 0x18*r = 90 + 24r.
  - Row strip sprite `0x58baf8` at (xoff+0x52, y_r) = (32, y_r), every row.
  - Value text left aligned at (xoff+0x57, y_r+7) = (37, y_r+7), font 0x51b360, colour 0x80000000 black, drawn only if v != 0. Text = sign + itoa(v*10) + percent: for v in 1..9 the sign literal is `DAT_004c5340`, for v >= 10 the sign literal is `DAT_004e9a84` (the empty string, EXACT: it is the filler used when `param_1 != 1` in FUN_0040daa0 for "Championship"). `DAT_004c60c4` is the percent literal. So "+10%" ... "+90%" (needs `DAT_004c5340 == "+"`, WEAK but matches the screenshot note "+50%"), and "100%" for 10.
  - Name text left aligned at (xoff+0x8a, y_r+7) = (88, y_r+7), colour `0x80004210 + (v != 0 ? 0xffffbdf0 : 0)` i.e. grey 0x4210 when v == 0, black when v != 0 (arithmetic wraps: 0x80004210 + 0xffffbdf0 = 0x80000000).
- Names (EXACT order, pointer table 0x4c2c3c..0x4c2c64, ten entries): Power Hitter, Long Driver, Accurate Driver, Accurate Irons, Accurate Putter, Draw Shot (R to L), Fade Shot (L to R), High Backspin Shot, Recovery Skills, Luck. (Entries 1 and 6..9 spellings are from screenshots in DECODE_CARDS2, only entry 0 "Power Hitter" appears as a literal symbol.)
- Skill value v: `0x5795a8[slot*0x100 + r]` when slot has a real profile, else (slot -1 or profile byte `0x57956e == 0`) the player's copy `0x5a59fa + 10 + r`. Values are 0..10 "points", shown as 10 percent steps.
- Latent oddity (EXACT, harmless): in read-only mode the mouse variables are not initialised but the hover-sprite test still runs; the compiler left `local_300` unset. Do not port any hover feedback in read-only mode.
- Skill-points line (editable only) = number + literal at `DAT_004d3c4c` + " skill points " (`s_skill_points__004d3c3c`). The `004d3c4c` literal is NOT IN DUMP; it is the text before the number ("Add " in the port from the screenshot; WEAK).

## 2. Golfer card buttons: Customize and View Story

### 2.1 What the dump contains (EXACT)
- All five button states are drawn by FUN_0045c560 only. The click action is NOT IN DUMP: no code reads `DAT_00824130` (the hover id) outside FUN_0045c560, and FUN_0045c560 has no caller in the dump (the caller region 0x4103xx to 0x421b5f is missing, as DECODE_CARDS2 says). So nothing here proves what a click does. Everything below about "what each does" is inference, flagged.
- `DAT_00824144` (the partner-layout enable) is read only inside FUN_0045c560 (never written in the dump): NOT IN DUMP.

### 2.2 Customize (button id 0, tooltip literal `s_Customize_004d39c8` "Customize")
- Enabled: always drawn and hit-testable in both layouts (S: icon (0x125,0xed), hit centre (0x13e,0x106); P: icon (0x10d,0x10e), hit centre (0x126,0x11f)). No condition in the draw code.
- Action (WEAK, by elimination): the only routine that matches is the character editor `FUN_004385d0(charRecord, golferSlot)` (docs/DECODE_CUSTOMISE.md). Its ONLY two call sites are in `FUN_00436060` case 0 (dock Player panel button, lines 29830 to 29845), both `FUN_004385d0(0, 0x98)`, and before them the code writes `type = 0x20` into slot 0x98 and the three clothing toggles. The routine edits char record 0 (the player's character) and golfer slot 0x98 only. So Customize on the info card either opens that same editor for the player's own golfer, or does nothing useful for other golfers; the dump cannot show which. Recommendation for the port: enable Customize only when the card's golfer is the player's own character (slot 0x98 / the pro-challenge golfer type 0x24), and leave it in the pale strip for everyone else (as the port does now).
- Confidence: code facts EXACT; "info card Customize == dock Customize" WEAK.

### 2.3 View Story (id 3, tooltip `s_View_Story_004d3978`)
- Layout S (single golfer, tooltip "View Story"): the icon at (0x1e8, 0xed) is drawn ONLY when the golfer has a partner: `0x579568[slot*0x80] != -1` (EXACT, line 61170). The hit test for id 3 and its tooltip are NOT gated, so the tooltip can appear over an empty slot (EXACT quirk; port should hide the tooltip too).
- Layout P (golfer with partner, partners enabled): button id 3 is relabelled "Golfer Comments" (`s_Golfer_Comments_004d3994`), icon (0x1d0, 0x110), hit centre (0x1e9, 0x11f). View Story is not shown in layout P; "Next Chapter" (`s_Next_Chapter_004d3984`, id 5, icon (0x14e, 0x110), centre (0x167, 0x11f)) takes its place.
- Meaning of "story" (EXACT facts): each golfer pair has a chapter counter `short@0x57956a[slot*0x80]` (0..4) and a progress counter `short@0x57956c`; both are advanced by `FUN_00466370(slot, force)` (line 69285), called automatically from the golfer update at line 19464 with force = 0. It returns 0 with no effect if no partner (`0x579568 == -1`), if either golfer has played fewer than 2 holes with 0 strokes (when force == 0), if both are already past chapter 3, or if `0x57956c <= chapter*4 + 4` (when force == 0). On success it increments the chapter, flags both golfers (`0x5794c8 |= 0x800000`), plays a story sound (ids 0x32.., 0x33/0x6e/0x73/0x78 by course theme `DAT_005a34e0` 0..3), changes mood +1 or -1 and may trigger a nearby-golfer kiss event (`FUN_004a0890`). When both chapters reach 4 the pair "ends" (`DAT_00561258 += 1`).
- Next Chapter: hidden and its hover id forced to -1 when both golfers' chapter shorts are 4 (EXACT, lines 61517 to 61525; the earlier docs called the field "byte state"; it is a short, chapter number). Shown otherwise. The action is NOT IN DUMP; WEAK: it calls `FUN_00466370(slot, 1)` (force skips the hole/progress gates; the only other caller passes 0).
- View Story action: NOT IN DUMP. The strings that pair with it are story lines kept in the golfer record: ids at `0x579528[slot*0x100 + 0..9]`, details at `0x579532[...]`, rendered by `FUN_00469b00(id, mood_word & 0x3fff, detail, slot)` into text lines drawn on the card itself (see 2.5). A "story file" with `MYNAME` and `PARTNER` placeholders is substituted by `FUN_0045b7c0` (line 59209, calls at 60025/60026 and 80151/80152). WEAK: View Story shows that story text for the pair (the theme packs have a Stories file type, `Themes\<pack>\*.txt`, DECODE_TITLE2 section 4). Format of that file: NOT IN DUMP here.
- Port advice: draw the View Story button only when the golfer has a play partner (pair in the same group); otherwise leave the strip pale and hide the tooltip. Customize likewise as above.

### 2.4 Button art (EXACT sheet, DERIVED index)
The info card buttons are cut from `Interface/GolferStats.pcx` (+ `_A`), loader lines 40733 to 40790. After plate A (64,33,402x244) and plate B (64,300,402x138) comes a grid of 57 x 50 tiles: columns x = 500, 600, 700 and rows y = 0, 50, 100, ... (10 rows, 30 sprites). Sprite index i = row*3 + col with the sprite blocks used by the card at index 0 (Customize), 6, 9, 12, 15 (layout S ids 0..4), 18 (Next Chapter), 21 (Golfer Comments), 24 (P snapshot), 27 (P id 4); i.e. each button owns a whole ROW of three tiles: normal, hover (+1 sprite = +0x2c), and a third (probably disabled or pressed, never drawn in the dump). That matches the port's existing `kCardBtnRow {0,2,3,4,5}` (rows 0, 2, 3, 4, 5 = indices 0, 6, 9, 12, 15) and means rows 1 (indices 3..5) is the unused or alternative set. DERIVED (the cut destination is hidden but the 0x2c address deltas fit 3-per-row exactly: 0x567498-0x567390 = 6 sprites, etc.). A second identical set exists for the shadow/colour sheet pair (arrays 0x567390 and 0x56a948).

### 2.5 Other things found on the card while here (EXACT)
- Comment/story lines under the scorecard: up to 5 lines at x=0xf8 (248), first y=0xaa (170), step 0xd (13), body font; the entries are taken newest first starting at index 4 (or index 9 when `param_2 != 0`), going down to 0, skipping empty ids.
